# Kit 00 · ADR 0002, each service picks its own database

Source: [`docs/adr/0002-database-per-service.md`](../../docs/adr/0002-database-per-service.md)

## 1. Pitch

I didn't pick one database for the whole system. Each service picks the one that fits its data. Proposals receives documents from dealers, and every dealer sends different ones, so I used MongoDB: it stores each document as it comes. Credit stores analyses with fixed fields, score, limit, decision, and the team wants to query that history, so I used MySQL. My first decision said one database instance for everything, but the real data showed two different shapes, so I wrote a new decision record instead of hiding the change. The price is two engines to operate. And the rule didn't change: a service never reads another service's database, only its API.

## 2. Interview Q&A

**Q: Why did you use two different databases?**
Because the two services have different data. Proposals stores documents from dealers, and each dealer sends different fields, sometimes a type we have never seen. A document database stores them as they come. Credit stores analyses with the same fields every time, and the team wants to query and compare decisions, so a relational table fits. I let each service pick from its own data, not from what the others use.

**Q: Isn't it expensive to run two database engines?**
Yes, that's the trade-off. Two engines to learn, back up and monitor. For two services with such different data, I think it pays off. If the data were similar, I would keep one engine. PostgreSQL with JSONB was a real option to have only one, and I would choose it if the documents were a small side part of the data. In proposals they are almost all of it.

**Q: What do you do when you find out an earlier decision was wrong?**
I write a new decision record. My first ADR said one database instance for all services. When the second service came, its data didn't fit that, so I wrote ADR 0002, which amends the first one. I don't edit the old record, because the history of why we changed is useful for the next person.

## 4. Glossary

| Term | Meaning | Example |
| --- | --- | --- |
| database engine | the software that stores the data | MongoDB and MySQL are two database engines. |
| document database | stores records as JSON-like documents, each with its own fields | A document database accepts a document type it has never seen. |
| relational database | stores data in tables with fixed columns | Credit uses a relational database for its analyses. |
| polyglot persistence | different database engines for different services | Hermes uses polyglot persistence: MongoDB and MySQL. |
| JSONB | PostgreSQL's binary JSON type, which can be indexed | JSONB was the main alternative we considered. |
| amend | to change part of an earlier decision with a new record | ADR 0002 amends ADR 0001. |
| fixed schema | every record has the same fields | A fixed schema protects the history of decisions. |
| trade-off | what you give up to gain something | The trade-off is two engines to operate. |
