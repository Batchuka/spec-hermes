# Kit 00 · ADR 0001, the overall architecture

Source: [`docs/adr/0001-architecture.md`](../../docs/adr/0001-architecture.md)

## 1. Pitch

At my last company I designed an architecture for import processes, and this project rebuilds it on a financing process. A farmer asks for credit to buy a tractor. Three services do the work: proposals, credit and contracts. They don't know about each other. A fourth service, the orchestrator, is the only master. I took the idea from industrial networks, where I come from: one master and a shared bus. The orchestrator publishes a command on a TX bus in EventBridge, a rule delivers it to the right service's queue, and the service answers on an RX bus. Everything on RX goes to one SQS queue that only the orchestrator reads. The services stay independent, nothing is lost if one is down, and we always know where every proposal is.

## 2. Interview Q&A

**Q: Can you walk me through the architecture of a system you designed?**
I'll use a financing flow as the example. There are three domain services, proposals, credit and contracts, and an orchestrator. The services never call each other. The orchestrator sends commands on one EventBridge bus, the TX bus, and each command lands in the queue of the service that owns it. When the service finishes, it publishes the result on a second bus, RX, which feeds a single SQS queue read by the orchestrator. Then the orchestrator decides the next step. It's the same model as an industrial fieldbus: one master, everyone else answers.

**Q: Why orchestration and not choreography?**
With choreography every service reacts to the others, so the flow is spread across all of them. Nobody can tell you where a given proposal is, and changing the order of the steps means changing several services. With one orchestrator, the route is data in one place. The trade-off is that the orchestrator becomes critical, so its state is in a database and the queues hold the messages while it restarts.

**Q: Why not Step Functions?**
Step Functions is also an orchestrator, and it would work. In our case the route is declared by the business and can change without a deploy, so we kept it as data in a Spring service. I would pick Step Functions for a fixed workflow owned by engineering.

**Q: Why not Kafka?**
Kafka is a log. It shines with high throughput and when you need to replay events. Here we have a few events per second and no replay requirement, so a managed bus and queues cost almost nothing and need no cluster.

## 3. Follow-ups

1. What happens if the orchestrator goes down in the middle of a proposal?
2. How do you make sure a message is not processed twice?
3. How would you trace one proposal across all the services?
4. Credit was approved, but the contract failed. How do you undo it?
5. How would this design change at a hundred times the volume?

## 4. Glossary

| Term | Meaning | Example |
| --- | --- | --- |
| orchestrator | the service that decides the next step | The orchestrator sends one command at a time. |
| choreography | services react to each other with no central control | With choreography, the flow is spread across services. |
| event bus | a channel where events are published and routed by rules | Each command goes on the TX bus. |
| queue | a buffer that holds messages until a reader takes them | The command waits in the queue if the service is down. |
| at-least-once | a message is never lost but may arrive twice | SQS delivers at least once, so handlers must be idempotent. |
| idempotent | doing it twice has the same effect as once | The handler is idempotent: it checks the event id first. |
| correlation id | the id that ties all messages of one process | We use the proposal id as the correlation id. |
| saga | a long process of local steps, each with a compensation | Cancelling the contract is a compensation in the saga. |
| single point of failure | one part whose failure stops everything | The master is a single point of failure, so its state is persisted. |
| trade-off | what you give up to gain something | The trade-off is one more critical service. |

## 5. Frames

- `We chose ___ over ___ because ___.` → *We chose an orchestrator over choreography because we needed to know where every proposal was.*
- `The trade-off is that ___, so we ___.` → *The trade-off is that the orchestrator is critical, so we keep its state in MySQL.*
- `I would pick ___ when ___.` → *I would pick Kafka when we need high throughput and replay.*
