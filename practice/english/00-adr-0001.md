# Kit 00 · ADR 0001, independent services, one per business domain

Source: [`docs/adr/0001-architecture.md`](../../docs/adr/0001-architecture.md)

## 1. Pitch

I designed this system around the business domains. A farmer asks for credit to buy a tractor, and the work is split in three: proposals, credit and contracts. Each one is its own service, with its own code, its own deploy and its own schema in the database, so it's not a monolith. One Angular front end serves the three of them. I did the same thing at my last company: the business rules were clear, so each application could be built alone, and they fit together later. I kept the question of how they talk to each other for a later decision, because it should come from what the business needs.

## 2. Interview Q&A

**Q: Can you walk me through the architecture of a system you designed?**
I'll use a financing flow as the example. The business has three domains: proposals, credit and contracts. Each domain is a separate service with its own REST API and its own schema. They all use one database instance, but a service never reads another service's tables. One Angular app, served as static files, calls the three APIs. So the user sees one screen, and the team can change and deploy each domain alone.

**Q: Why microservices and not a monolith?**
The domains have different rules and different data. Contracts handles money and needs strong transactions. Proposals handles documents with different shapes. In a monolith they change and deploy together, and the boundaries slowly disappear. The trade-off is that there is more to run, so we kept the infrastructure small: one database instance and one front end.

**Q: Why one schema per service and not one shared database?**
If services share tables, a change in one can break the others. With one schema per service, the only way into a domain is its API. We still use a single instance, because it is cheaper for a demo, and the schemas can move to separate instances later without changing the services.

**Q: What did you leave out on purpose?**
How the services work together in one process, for example approving credit and then issuing the contract. I didn't want to decide it before the business asked. At my last company the applications were built first, and the integration came later, when the need was real.

## 4. Glossary

| Term | Meaning | Example |
| --- | --- | --- |
| domain | an area of the business with its own rules and data | Credit is a domain with its own rules. |
| monolith | one application that holds all the domains | A monolith deploys everything together. |
| microservice | a small application that owns one domain | Each microservice has its own repository. |
| schema | a named set of tables in a database instance | Each service owns one schema. |
| boundary | the line a domain does not cross | The only way across the boundary is the API. |
| Jamstack | a static front end that calls APIs | The Angular app is static, in the Jamstack style. |
| REST API | an HTTP interface organized around resources | Each service exposes a REST API. |
| coupling | how much one part depends on another | A shared table creates coupling between services. |
| deploy | to publish a new version | We can deploy credit without touching contracts. |
| trade-off | what you give up to gain something | The trade-off is that there are more things to run. |

## 5. Frames

- `We chose ___ over ___ because ___.` → *We chose separate services over a monolith because each domain has its own rules.*
- `The trade-off is that ___, so we ___.` → *The trade-off is that there are more things to run, so we use one database instance.*
- `I would pick ___ when ___.` → *I would pick a monolith when the team is small and the domains are not clear yet.*
